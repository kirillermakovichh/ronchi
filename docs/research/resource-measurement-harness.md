# Resource measurement harness

This note describes the local harness for task 24 and ADR-0019.
It does not contain resource measurements or new release gates.
Task 24 remains open until the integrated executable passes the recovery checks and produces reviewed observations.

## Prerequisites and commands

Use macOS or Linux with Python 3.11 or later.
Prepare the embedded dashboard assets before building Ronchi.
Use the final integrated release executable for resource evidence.
Stop competing development builds and test suites before the measurement run.
Record other host work in `--host-load-note`.
Do not terminate unrelated user processes.

```sh
npm --prefix dashboard ci
npm --prefix dashboard run build
cargo build --release --locked
python3 scripts/measure-resources.py \
  --binary target/release/ronchi \
  --output /private/tmp/ronchi-resource-observations.json \
  --build-revision INTEGRATED_COMMIT \
  --build-command 'cargo build --release --locked' \
  --host-load-note 'Describe actual uncontrolled host work here.'
```

Replace `INTEGRATED_COMMIT` with the executable's source commit.
If a pinned native archive is available, add `--surfpool-archive /absolute/path/to/archive.tar.gz`.
The harness installs the archive into its disposable project through the ordinary checksum-verified installer.
It runs simulator mode and Surfpool mode separately.
It does not download an archive or use a public RPC endpoint.

Use `--smoke` for a short harness check.
If the executable is a debug build, also use `--build-profile debug`.
Declare the actual debug build command with `--build-command`.
The report classifies smoke output as `harness_smoke_not_resource_evidence`.

```sh
python3 scripts/measure-resources.py \
  --binary target/debug/ronchi --build-profile debug --smoke \
  --build-command 'cargo test --locked --test failure_recovery' \
  --output /private/tmp/ronchi-resource-smoke.json \
  --host-load-note 'Harness check during development; load is uncontrolled.'
```

## Workload and observations

The default run uses 100 requests, concurrency four, ten queries per query phase, three idle seconds, and a 100 ms sample interval.
Arguments bound request counts, concurrency, idle time, and sampling frequency.
The report records the selected values and operational limits.
It records binary size, SHA-256, declared revision/profile/build command, host compiler version, platform, CPU count, load averages, and the host-load note.
The declared build metadata must match the executable; the harness cannot infer compiler flags from a binary.

| Phase | Observation |
| --- | --- |
| Idle | Core RSS samples and process CPU-time delta; optional Surfpool child samples remain separate. |
| RPC reads | `getSlot` latency, output bytes, completed requests per second, and committed Journal events. |
| Fake source baseline | Direct loopback `getBalance` calls compared with the same source through Ronchi in simulator mode. |
| Large response | A fake `getAccountInfo` result near the 256 KiB response limit, with sampled process RSS. |
| Timeout Case | Repeated `getLatestBlockhash` calls across short outage/recovery cycles, including transport outcomes. |
| Dashboard during writes | HTTP Investigation query latency while a bounded RPC workload commits Journal events; raw intervals show overlap. |
| Live CLI and MCP | Summary/timeline latency and output bytes; MCP uses real stdio initialization and `tools/call`. |
| Retained history | Summary/timeline CLI queries and a real MCP summary query after Lab shutdown. |
| Disk | Logical and allocated bytes per retained file; phase event counts and observation-time event rate. |

Each process has its own RSS and CPU observations.
The harness samples the core, owned Surfpool children, and live MCP adapters separately.
It excludes the Python load generator and fake source from core RSS.
CLI latency includes process startup; it does not report transient CLI peak RSS.
MCP query timing excludes initialization; the report records the protocol path used for initialization.
Idle CPU is a process CPU-time delta, not an instantaneous utilization percentage.
RSS peaks are sampled maxima, not OS true peak measurements.
The sampler checks the observed process birth identity within and across phases.
On macOS, `ps lstart` has second-level birth precision; Ronchi owns exact process identity checks for shutdown.

Every HTTP request opens a fresh connection.
The Python source and client add overhead to the direct/source comparison.
Readiness is the only warmup.
The retained history consists of the bounded workload generated by that run.
Use larger explicit request counts when investigating retained-history scale.
These observations do not establish production throughput or a warm pooled-client baseline.
The Journal event rate includes evidence events; it is not a raw SQLite write benchmark.
Allocated bytes can change because of WAL checkpoints and filesystem allocation.

The harness stores raw latency observations and process samples in a new JSON file.
It refuses to overwrite an existing report.
It keeps bearer tokens, browser tickets, and session cookies in memory.
It does not put those credentials or credential-bearing URLs into the report.

## Failure and cleanup

The harness uses disposable projects and loopback fixtures.
It stops each Lab through the ordinary CLI ownership checks.
If termination cannot be established, it retains the project and records its path.
It does not signal a process solely because a stored PID exists.
An incomplete run records the failed phase and returns a nonzero exit code.
Review sampler errors and dashboard/write overlap before treating a run as evidence.
Do not combine results from smoke runs with resource evidence.

`tests/failure_recovery.rs` separately exercises real SQLite writer failure and a sparse-file Lab quota failure.
Both tests acknowledge signed transaction bytes before failure.
They require whole-process fail-stop, retained signed bytes, and survival of an independent reference relayer.
The quota fixture exceeds only the disposable Lab's accounting limit.
It does not fill the host disk.
The parsed-response batch regression covers a valid packet whose aggregate evidence must stay bounded.
These tests preserve a failed fixture for diagnosis.
